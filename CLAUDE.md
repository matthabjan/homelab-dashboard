# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Self-hosted homelab status page and launcher (SvelteKit 2 / Svelte 5, Node adapter, Node ≥ 22.13, image ships Node 24). Reads gethomepage-compatible YAML, polls Proxmox VE, PBS, OPNsense, OpenMediaVault, AdGuard Home, Pi-hole, Portainer, Docker (socket proxy), What's Up Docker, Home Assistant, FRITZ!Box and any JSON API (`customapi`), and pushes one JSON snapshot to browsers over SSE.

## Commands

```bash
npm ci
CONFIG_DIR=config.example DEMO=1 npm run dev     # http://localhost:5173 with fixture data (DEMO_SCENARIO=calm for all-healthy)
npm test                                         # node --test over src/**/*.test.ts (Node strips the types; no build step)
node --experimental-strip-types --test --test-name-pattern=calm src/lib/server/integrations/integrations.test.ts   # one scenario (the pattern matches top-level test names only)
npm run check                                    # svelte-kit sync + svelte-check (strict TypeScript, .ts and .svelte); there is no linter
npm run build && DEMO=1 CONFIG_DIR=config.example npm start   # production build on :3000
docker build -t homelab-dashboard:local .
```

CI (`.github/workflows/ci.yml`) runs `check` and `test`, then builds the image and smoke-tests it in demo mode (`/api/health`, `/api/state`, `/`) on every push and PR; PRs from `development` to `main` are skipped, since the push run covered that tree. All must pass. Images are built once: on `main` and tags the `plan` job checks whether `:dev` was built from the same tree (its revision label) and, if so, `promote` adds the tags to that digest instead of checking and building again.

## Architecture

One Node process, no worker or external DB. `src/hooks.server.ts` starts a singleton `Engine` (`engine.ts`, kept on `globalThis` so dev HMR doesn't duplicate it) and stops it on SIGTERM/SIGINT. All server code is in `src/lib/server/`; shapes (`Snapshot`, `Tile`, `WidgetResult`, `Sources`, …) in `src/lib/types.d.ts`. Domain terms (service, widget, integration, ctx, transport, fixture, scenario, attention, feed, storage row, removable datastore) are defined in `CONTEXT.md`; use them.

- **Engine.** Loads the config, watches `CONFIG_DIR` for `*.yaml` changes, and runs four rounds: probes and widgets on `settings.intervals`, certificates, icons hourly. Every round starts through `round(name)`, which skips a tick while the same round still runs. It reads the outside only through its `Sources`: `liveSources` (`sources.ts`) or `demoSources()` (`demo.ts`). `getEngine()` picks them by `DEMO`, and nothing below checks `DEMO`: the engine passes `Sources.demo` to `loadConfig({ demo })`, which records it as `cfg.demo`. After each round `publish()` rebuilds the snapshot and emits `update`; `/api/stream` sends it to SSE clients (serialized once per snapshot), `+page.server.ts` uses it for SSR. `stop()` clears the timers and emits `stop`, which ends the open streams, so `docker stop` exits at once. `engine.test.ts` runs rounds by hand on scripted sources.
- **Integrations** (`integrations/<type>.ts`) export `collect(widget, ctx)` → `WidgetResult` (`stats`, `line`, `alerts`; optional `events`, `storage`, `drives`, `host`, `network`, `dns`, `backups`, `containers`, `discovered`). They reach the outside **only through `ctx`** (`createContext` in `integrations/index.ts`): `getJson`/`request` transport, `kv` (durable), `state` (per service), `shared` (between integrations), `metric`, `settings`, `now`, `insecure`. `ORDER = ['proxmox']` runs first because it puts guest ids in `ctx.shared` for PBS backup freshness; the rest run in parallel, each with a 25 s timeout.
- **Fixtures** (`demo/<type>.ts`) are `"METHOD /path"` → `({ now, scenario, params, headers, body })` tables served by `fixtureTransport`. Demo mode and the tests use the same transport seam, so integrations run unchanged in both. `demoSources` only fakes what has no integration: probes, certificates, local host, temperatures, 24 h of seeded history.
- **Checks** (`check.ts`): `record` turns a reading into check state, a history row and events; `status` gives the tile's level, line and alert. `siteMonitor` is probed over HTTP (<500 = up) or, for `tcp://host:port`, by connecting. **Heartbeats** (`heartbeat.ts`, `/api/heartbeat/<id>[/fail]`) are push checks: token compared on SHA-256 digests, 404 for an unknown id or a wrong token, 1 call/s per id; results live in `kv`.
- **Snapshot** (`snapshot.ts`) holds the status rules: down after 2 failed probes, "slow" when the 1 h p95 exceeds `latencyWarnMs` with ≥10 samples, the certificate and temperature thresholds, the verdict, the fleet strip. `build` runs one function per panel. Those that raise alerts (`configAlerts`, `serviceTiles`, `hostPanel`, `storage.ts`'s alerts, `drivesPanel`) run before `round.close`, the rest (`applyWorst`, `networkPanel`, `fleetStrip`, `verdictOf`, `mostUsedRow`) after. The infrastructure strip's cells and the sheet's tabs come worded and judged from `infrastructure.ts` (`snap.infrastructure`), the Storage cell, the storage rows and the Disk gauge's level from `storage.ts` (one alert per disk, `storage.test.ts`), the Backups cell and the Backups tab (`snap.backups`, with `days`: a level per day of the last week: red where a backup job was found late, green where a job was on time or a backup completed; the services' other events never count) from `backups.ts`, which adds up what `pbs.ts` and `check.ts` judged (tested on its own in `backups.test.ts`); the page only renders them. History queries go through `perMinute` (read once a minute per builder); live state is never cached. Tested through `build` in `snapshot.test.ts`, with inputs from `test-helpers.ts#snapshotInput`.
- **Main page** (`+page.svelte`): the top card (`verdict`: one sentence with See details and the top item's Open action; beside it every crit/warn item once, as a list with a filter by level; when calm, Most used instead), the infrastructure strip (a cell each for System, Storage, Drives, Network and Backups: figure, a small picture drawn from what the sheet charts, context; a problem colours the figure and adds its shape; on phones a compact list, a row per area with the picture on the right and the context only for a problem) and the services as **tiles**: every service and job with its icon, name and status line. A tap on a tile opens the service; the button at its end or a long press (`longpress` action, touch only) opens its sheet; one without `href` opens its sheet on a tap; a Problems filter narrows the list. Activity lists what happened and folds the info items (notes) into one row; Links sit under it. Details live in sheets (`Sheet.svelte`, a modal `<dialog>`; on phones no X but a handle that closes; one fluid drag: the top edge follows the finger, and on release it carries on with the finger's speed and stays where it lands, closed below a third of its opening height or on a quick flick): a service (with its 7-day events from `/api/events?sid=`), infrastructure (`Infrastructure.svelte`, five tabs; the Backups tab's body is a snippet from the page, since its rows open service sheets) and activity (`feed`). Each Activity row carries `open`, the sheet it opens (`snapshot.ts#feedTarget`). Both pages share `AppHeader.svelte` (brand, search, live state, theme, Setup) and, on phones, `TabBar.svelte`. Below 760 px the dashboard shows one view at a time (Home, Services, Alerts): each section names its views in `data-v` and CSS hides the rest, so the markup stays one. The view is history state (`page.state.view`): leaving Home pushes an entry, switching between the others replaces it, sheets push on top. Search opens the palette, full screen on phones; Setup's tab bar leads here by hash (`/#search`, `/#view-services`, `/#view-alerts`). The theme button sits next to Setup in the header (`ThemeToggle compact`, one button stepping through system, light, dark); Setup also has the three-way toggle, and the two keep in step.
- **Attention** (`attention.ts`): `begin(now)` → `raise({ sev, key, title, service | source })` → `close(events)`; raising after close throws. It names, ages (by key, never by title) and orders alerts, and gives the headline, the feed, `needCount` and `worst(sid)`. `Alert.key` is required and unique per widget result (`integrations.test.ts` checks it).
- **Config** (`config.ts`): `loadConfig()` deep-merges `settings.yaml` over `DEFAULT_SETTINGS`; intervals below their minimum become problems. `${NAME}` and `{{HOMEPAGE_VAR_NAME}}` resolve from the env, then `NAME_FILE`, then `/run/secrets/<name lowercase>`. A broken file keeps its last version and is recorded as a problem. Missing secrets are recorded by name (not in demo mode).
- **Config view** (`/config`, `config-view.ts`) is read-only and **allowlist only**: type, URL origin, per-type `SAFE_OPTIONS`, status. `config-view.test.ts` fails if any configured secret reaches the page data. The page (titled Setup) checks the configuration, not service health: it joins `widgets`, `checks` and `icons` onto `services` (one row per service) and shows settings that differ from the default first. A row opens the service's setup details in a sheet (`page.state.setup`); the page data also carries `shell` (logo, alert count) for the shared header and tab bar.
- **Label discovery.** Portainer and Docker (`integrations/containers.ts`) turn `dashboard.*` container labels into `discovered` services; `config.withDiscovered` merges them, and services.yaml wins on the same group and name. Label values are never secret-substituted.
- **Icons** (`icons.ts`): a service without `icon` gets one from the selfh.st or dashboard-icons index (fetched daily into `kv`). Candidates in order: name, container image, widget type, leading words of the name, each matched with or without hyphens. The base icon is used in both themes unless its colours have under 1.5:1 contrast with the icon chip in one; then the light or dark variant replaces it there. selfh.st variants are taken by name, dashboard-icons variants are measured, since their names are unreliable. An `icon` set by its index name without `iconDark` (services and bookmarks) gets the same check (`variantOf`, kept in `engine.iconVariants`).
- **App icon** (`default-images.ts`, `default-images/`): the icon ships with the app and is served under `/assets/images/` where the config has no file of that name, or only an old stock copy (known by hash); a file the user put there wins. `pwa.logoDark` and `pwa.faviconDark` name dark-theme variants; unset, the app's own mark is used while the light one is the app's own too (`config.ts#darkAssetUrl`).
- **HTTP** (`http.ts`): undici agents with `cachedLookup` (DNS answers kept 5 min, all addresses handed to Node so a dual-stack host falls back to IPv4).
- **Storage** (`db.ts`): built-in `node:sqlite` at `DATA_DIR/dashboard.db` with tables `probes`, `metrics`, `events` (a check's down/recovered events carry `outage`, when it began, so `check.ts#withoutBlips` can keep short ones out of Activity), `opens` and `kv`, pruned to `retentionDays`. Service ids are `slug(group-name)`, so renaming a service resets its history.

## Adding or changing an integration

- **Register every type in three places** or `integrations.test.ts` fails: `INTEGRATIONS` (`integrations/index.ts`), `FIXTURES` (`demo/index.ts`) and `WIDGETS` in the test.
- **Fixtures cover both scenarios:** `issues` triggers the alerts, `calm` is healthy.
- **Update the examples and docs:** `config.example/services.yaml`, a commented example in `config.starter/services.yaml` if it's useful without Proxmox, and `docs/integrations.md` (least-privilege account, options, alerts).
- **Field names** match gethomepage's widget fields.
- **Build `stats` and `line`** with `format.ts#card` from `[Stat, text]` facts, so the status line (Status view, problem cards) and the service sheet (the stats) say the same.
- **Alert text is shown to every viewer:** never put credentials or upstream bodies in it. Throw short messages and attach the body as `err.body`, which is only logged.

## Conventions

- TypeScript in strict mode, `<script lang="ts">` in components, no `any` (use `unknown` and narrow). Shared shapes go in `types.d.ts`, imported with `import type`. Svelte 5 runes; props typed with an `interface Props`.
- Tests run the `.ts` sources with Node's type stripping, so relative imports name the `.ts` file (`./db.ts`), only erasable syntax is allowed (`erasableSyntaxOnly`), and type-only imports use `import type`.
- External API shapes (`PveNode`, `AdguardStats`, …) live in their integration's file, exported; fixtures return them, so a drifting fixture fails `npm run check`. Read them with `ctx.getJson<T>()`.
- Runtime dependencies are only `yaml` and `undici`; avoid adding more.
- CSP is nonce-based (`svelte.config.js`): no inline scripts or `javascript:` URLs. The service worker never intercepts page loads or `/api/*`, because of basic auth prompts.
- Every section is one markup for both layouts: the tiles are a grid above 760 px and rows below, and the phone's views only hide sections (`data-v`). Don't duplicate sections per layout.
- **Two configs.** `config.example/` is the full demo (`DEMO=1`; in the image at `/app/config.example`, picked via `DEMO_CONFIG_DIR`). `config.starter/` is the image's `/config` and must work with zero edits on any Docker host (CI checks it). Neither holds images: the icon is built in.
- **This repo is public.** Examples, fixtures, docs and screenshots use generic names only (`*.home.arpa`, `example.com`, demo mode), never the maintainer's real hosts, IPs or setup. Local `config/`, `.env`, `compose*.yaml`, `secrets/` and `data/` are gitignored.
- **Docs:** `README.md` (synced to Docker Hub on release, so it must stand alone), `docs/configuration.md`, `docs/deployment.md`, `docs/integrations.md`, `CONTRIBUTING.md`. Update them when behavior or config changes.

## Branches and releases

Work on `development` (image `:dev`), PR to `main` (`:edge`). To release: bump `version` in `package.json`, merge to `main`, push tag `vX.Y.Z`. The workflow checks the tag against `package.json`, promotes the `:dev` image (or builds, if `development` has moved on), publishes `X.Y.Z`/`X.Y`/`X`/`latest` to Docker Hub (`matthabjan/homelab-dashboard`), and creates the GitHub Release. Dependabot targets `development`; majors are upgraded deliberately.
